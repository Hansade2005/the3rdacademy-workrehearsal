## LAYER 1: Universal Architecture
What every BridgeFast dimension module must contain, regardless of dimension, tier, or sector. These elements are non-negotiable. A module that does not contain them is not a T3A dimension module.

### §1.1 — Required Segments (A through G)
Every module has seven segments. The letter, name, purpose, and order are fixed across all modules.

| **Segment** | **Name** | **Purpose** |
| --- | --- | --- |
| **A** | Cold Open + Safety Floor + Central Question | Drop the participant into pressure within 90 seconds. Provide the safety floor. Anchor the central question that returns at module close. |
| **B** | Behaviour Standard | Establish the dimension's professional behaviour standard. Brief, foundational, sets the conceptual frame. |
| **C** | Recognition Briefs (2–3 briefs including the dimension's signature framework) | Frameworks named after cold-open experience, never before. Recognition before naming. |
| **D** | Audio Case | Real workplace story with 1–2 standard decision points (plus declared dimension-specific signature pauses, if any). Bridges Segment C briefs to Segment E scenario lab. |
| **E** | BehaviourLab Scenario Lab (4 scenario chains) | The core of the module. 4 chains, each with 1 decision point, 3 decision paths, 3 consequence horizons. |
| **F** | Micro-Drills | Two short rehearsal drills. Drill type is dimension-specific (e.g., message rewrite, response repair, escalation drill, manager interpretation drill). Consolidates the scenario-lab content. |
| **G** | Completion + Awe-Moment Close + Retention Check | A single moment the participant carries out. Witness, do not explain. Sets up retention check 3–7 days later. |

> **🔒 LOCKED RULE — Segment order and purpose are fixed**
>
> The 7-segment architecture is universal across every BridgeFast dimension module. A module may NOT add an eighth segment, remove a segment, or reorder them. Within each segment, dimensional calibration applies — but the segment frame is locked.

### §1.2 — Required Runtimes and Pacing
| **Segment** | **Target runtime** | **Tolerance** | **Pacing note** |
| --- | --- | --- | --- |
| **A** | 2:40 | ±15 sec | Hard cap — must not bloat. The cinematic discipline is the point. |
| **B** | 8:00 | ±2 min | Compressed behaviour-standard treatment. Not an academic paper. |
| **C** | 12:00 | ±3 min | 2–3 Recognition Briefs including signature framework reveal. |
| **D** | 10:00 | ±2 min | Audio case + 1–2 decision points (plus declared dimension-specific signature pauses, if any) + reflection. |
| **E** | 45:00 | ±5 min | 4 scenario chains × ~11 min each. Core of the module. |
| **F** | 9:00 | ±2 min | Two micro-drills + brief reflection. |
| **G** | 5:00 | ±30 sec | Hard cap. Recognition + framework return + Growth Log (with final Pattern Ledger state) + retention check + awe close. Five screens. |
| **TOTAL** | **~89:00** | **90 min** | **Marketed and sold as 90 min per module.** |

> **🔒 LOCKED RULE — Hard caps on Segment A and Segment G**
>
> Segments A and G are the cinematic boundaries of the module. Their power comes from compression. Segment A holds a ±15-second tolerance because the cold-open pressure cannot bloat. Segment G holds a ±30-second tolerance because it must contain five screens — recognition, framework return, Growth Log review with the final Pattern Ledger state, retention check setup, and the awe close — while still feeling like a single quiet moment. Segments B through F have looser tolerances because dimensional differences may require slightly more or less narrative breath.

> **🔒 LOCKED CLARIFICATION — Segment A may include a separate consequence screen**
>
> Where the cold open includes an immediate participant decision, the same-day consequence may be rendered as a separate Screen A-2 before the safety floor. This preserves the sequence: pressure → decision → consequence felt → safety floor → central question. The separate consequence screen is moat-critical because it lets the participant feel the weight of the decision before reassurance is introduced. It must not be collapsed into the cold-open screen for convenience. The 5-screen pattern (A-0 through A-4) is the recommended pattern for modules whose cold open carries a participant decision; the 4-screen pattern (A-0 through A-3) remains valid for modules whose cold open is observational rather than decisional.

### §1.4 — Engine and Content Separation
> **🔒 LOCKED RULE — One engine. Many modules. Content is data, not code.**
>
> This is the single most important architectural principle in this standard. The BridgeFast engine is built once and reused across every module T3A ships — current and future. Modules differ only in their content. The engine never knows which dimension it is rendering; it simply parses the schema, runs the flow, and surfaces the right text at the right moment. Violating this separation forces engine drift, multiplies maintenance cost, and breaks the universal-architecture promise.

Three rules govern the separation:

- **1. The engine is dimension-blind. **The engine does not contain D1 logic, D2 logic, or any dimension-specific behaviour. It contains the universal flow only. If a piece of code references a specific dimension by name, that code is in the wrong layer.

- **2. Content does not contain engine instructions. **A module's content layer specifies WHAT the participant sees, not HOW it is rendered. If a module needs a new rendering behaviour, that is an engine update (rare and deliberate), not a content workaround.

- **3. New modules must not require dimension-specific hardcoded engine logic. **Any new module — D3 Foundational, a D2 Intermediate, a healthcare Custom pack — must load into the existing engine without dimension-specific hardcoded logic. Reusable engine extensions (for example, the Pattern Ledger, three-horizon consequence threading, and cross-module memory) are permitted only through versioned approval; once approved, they become general engine capabilities available to every future module, not one-module workarounds. If a module requires dimension-specific engine logic that cannot be generalised, the content — not the engine — violates the standard.

**Worked example — how the principle plays out in production**

Suppose during D3 Execution Reliability production, the producer realizes the module needs a recurring "deadline status" indicator that pulses red when the participant misses a check-in. The temptation is to ask Hans to add a deadline-pulse component to the engine.

- **Wrong move:** Add a deadline-pulse component to the engine specifically for D3. Now the engine contains dimension-specific logic, drifts away from D1's specification, and creates technical debt that compounds with every future module.

- **Right move:** Recognize that "deadline status" is a generalizable visual artifact element. If multiple modules will need urgency indicators (D4 communication has "message read receipts," D8 resilience has "recovery countdown," etc.), then formalize it as a versioned schema extension — an `artifact.urgency_indicator` field added through the §1.5 extension namespace, with engine support that ALL future modules can use. The engine stays universal. Content stays declarative.

**The engine acceptance test**

Module content must load into the existing engine without code changes. If any field in a new module requires engine modification to render, either the field is wrong or the engine specification needs to evolve THROUGH the versioned-extension process before that module ships. Engine modifications happen rarely, deliberately, and benefit the whole framework — they are never a per-module activity.

### §1.4.A — Cross-Module Memory (Engine Specification) [MOAT-CRITICAL]
Cross-module memory enables a subsequent module to reference what the participant did, said, or wrote in a previous module. The most visible use: D2's cold-open narration referencing the participant's D1 final personal sentence verbatim. The architectural value: a moat competitors cannot reproduce without rebuilding their data layer from scratch.

**Engine behaviour — the unambiguous specification**

- On module completion, the engine writes a participant emission contract to the cross-module memory store. The store is keyed by (participant_id, module_id). The contract is a standardised JSON object containing: cold_open_decision_path (a/b/c/d), scenario_decisions (array of 4 decision values), artifact_writes (array of verbatim text strings), audio_case_decisions (array of decision values), reflections (array of verbatim text strings), final_personal_sentence (string or null), module_completed_timestamp.

- On any subsequent module load, the engine queries the store for the participant's prior completed modules and loads their emission contracts into a session-scoped context object.

- The engine exposes prior data to the content layer through a templated callback syntax: {{prior.D1.final_personal_sentence}}, {{prior.D1.cold_open_decision_path}}, {{prior.D1.scenario_decisions[0]}}, etc. Content authors write these tokens directly into narration text and on-screen copy.

- At render time, the engine substitutes the token with the participant's actual value. If the referenced prior module has not been completed, the engine substitutes a content-declared fallback string (declared in the module's content alongside each callback anchor).

- The engine does not forward-reference. A module may only read from modules with a completion timestamp earlier than the current module's load timestamp.

**Input — schema fields the engine reads**

- prior_module.references[] — array of module_ids this module may read from (e.g., ["D1"])

- prior_module.callback_anchors[] — array of objects, each declaring: anchor_id, token (e.g., {{prior.D1.final_personal_sentence}}), fallback_string (text shown if the prior module was not completed)

**Output — what the engine produces**

- Persistent participant emission store, keyed by (participant_id, module_id), with the standardised JSON contract above

- Resolved templated values at module render time — the substituted strings appear in narration audio, on-screen text, and any artifact display where the content layer has placed the token

**Trigger — when this engine behaviour fires**

- Write: on module_completed event (Segment G submission)

- Read: on module load (before Screen A-1 renders)

**What this engine does NOT do (content responsibility)**

- The engine does not decide which prior data is relevant — the content layer declares which tokens to insert and where

- The engine does not generate or transform prior data — substitution is verbatim

- The engine does not surface Lock 2 fingerprint data through callbacks — Lock 2 stays internal regardless of memory layer

- The engine does not allow cross-participant references — a participant only ever sees their own prior data

**Acceptance criteria — concrete tests**

- Complete D1 as participant P1 with final_personal_sentence = "I will say the hard thing while it can still be heard." Open D2 content declaring callback token {{prior.D1.final_personal_sentence}}. The D2 narration renders with that exact sentence.

- Open D2 as participant P2 who has never completed D1. The same D2 narration renders with the content-declared fallback string (no error, no blank).

- Complete D2 as participant P1. Open D1 with a callback to D2 (forward-reference). The engine refuses the reference and uses the fallback string — forward references are blocked.

**[MOAT-CRITICAL] — Why this is non-negotiable**

No reviewed public competitor materials describe participant-written outputs being reused verbatim across later modules for narrative callbacks. The competitor data layers we have surveyed (Skillwell, Rehearsal, StratXSim, Cornerstone) appear from their public documentation to treat modules as discrete units, not as a cumulative chain. Cross-module memory is what creates the "this knew me" moment when a new hire opens D2 and hears the AI quote their own D1 sentence back to them. That moment is the single most visible differentiation in a five-minute buyer demo. Removing or simplifying it collapses the most important moat at the most important moment.

### §1.4.B — Two-Axis Variant Calibration (Engine Specification) [MOAT-CRITICAL]
Variant calibration uses two independent axes. Axis 1 (industry sector — Corporate/Finance, Healthcare, Construction/Trades, etc.) and Axis 2 (audience context — New Hire, Experienced Worker, Cross-Border Professional). The engine composes both at render time. The pairing of these axes is what allows T3A to serve a global, multi-industry market from a single module library.

**Engine behaviour — the unambiguous specification**

- On module load, the engine reads the participant profile to determine their (industry_sector, audience_context) tuple. The participant profile is set during onboarding and may be updated by the participant at any time before module start.

- The engine looks up the (industry_sector, audience_context) tuple in the module's variant_content_map.

- If the tuple has an exact match, the engine renders the matched variant's content (narration, scenario setup, artifact templates, consequence narrations).

- If the tuple has no exact match, the engine falls back to the module's declared default tuple. The fallback is always renderable — every module must declare a default that covers any participant.

- The variant chosen at module load is fixed for the duration of the session. The engine does not mix variants within a session.

**Input — schema fields the engine reads**

- module.sector_variants[] — array of supported industry sectors (existing field)

- module.audience_context_variants[] — array of supported audience contexts (new field). Must include "new_hire" as a minimum.

- module.variant_content_map — object keyed by (sector, audience_context) tuples; each value is a content delta over the module's base content

- module.default_variant_tuple — the tuple used when a participant profile has no exact match (e.g., {sector: "technology", audience_context: "new_hire"})

**Output — what the engine produces**

- Rendered module content using the resolved variant. All narration, scenarios, artifacts, and consequences for the entire session use the same variant.

- A logged event indicating which (sector, audience_context) tuple the participant received — for Lock 2 fingerprint and operational analytics.

**Trigger — when this engine behaviour fires**

- Variant resolution: on module load, exactly once. Fixed for the session.

**What this engine does NOT do (content responsibility)**

- The engine does not decide which variant a participant should receive — the participant profile + module declaration determines this deterministically

- The engine does not generate new variants — content writers produce them as schema-declared content deltas

- The engine does not blend variants within a session — one tuple, one session

- The engine does not require both axes to be exhaustively populated — modules may ship at MVP with one sector and two audience contexts, expanding later through schema updates

**Acceptance criteria — concrete tests**

- A participant declared as (healthcare, cross_border_professional) loads D1. The engine renders the healthcare scenario set with cross-border audience framing (e.g., explicit references to local protocol unfamiliarity, language-register differences) layered onto the healthcare workplace.

- A participant declared as (technology, new_hire) loads D1. The engine renders the default tuple — D1's primary Corporate/Finance scenarios or whichever default the module declares, with no audience-context overlay beyond New Hire baseline.

- A participant declared as (manufacturing, experienced_worker) loads D1 — but D1 has not declared a manufacturing variant. The engine falls back cleanly to D1's default tuple. The participant sees a complete, coherent experience. No broken state, no missing-variant error.

**[MOAT-CRITICAL] — Why this is non-negotiable**

The competitors we have surveyed appear, from their public positioning, to be either nation-focused or vertical-focused — serving enterprise L&D primarily within one country's market, often within one industry. T3A's two-axis variant calibration is the architectural commitment that "built in Calgary, for professionals worldwide" is a product claim, not a marketing claim. The Cross-Border Professional variant on Axis 2 is specifically what reaches the LMIA/AAIP buyer and the global newcomer audience no competitor serves at the scenario level. Removing the second axis collapses the global positioning before it has a chance to compound.

### §1.4.C — Signature Audio Brand (Engine Specification) [MOAT-CRITICAL]
T3A has two locked audio brand assets: the Tibetan singing bowl bell and a four-note motif. Both are engine-level assets played at fixed module locations across all 14 dimensions. They are sonic signatures that make T3A audibly recognisable. The bell and the motif do not vary per module. Their volume, pacing, and placement are engine-locked.

**Engine behaviour — the unambiguous specification**

- The engine holds two locked audio asset slots in its global configuration: audio.bell_asset_id and audio.motif_asset_id. Both are environment-level constants, NOT per-module schema fields. A new module ships without ever declaring these — the engine plays them at the locked locations.

- The bell plays at every consequence-horizon transition in Segment E. Each scenario chain (SC1 through SC4) has three horizons (Same Day → Next Week → Month End), giving two transitions per chain, eight bell strikes per module.

- The bell is a single strike, Tibetan singing bowl, fundamental ~528 Hz, ~3-second decay to silence, played at -12 dB relative to narration peak. These values are locked in the engine, not per-module parameters.

- The motif plays at three locations: (a) Screen A-0 entry, layered subtly under or just after the T3A wordmark fade-in; (b) Segment G G-4 Beat 2 silence, during the 2-second hairline fade — the motif begins as the question fades and resolves before the prompt appears; (c) Growth Log review page header, on first render only (not on subsequent visits within the same session).

- The motif is four notes, total duration ~3.5 seconds, played at -14 dB relative to narration peak. Specific composition (notes, instrument, voicing) is locked in the engine's audio asset, not in per-module content.

**Input — engine configuration (NOT per-module schema)**

- audio.bell_asset_id — environment constant, points to the locked bell audio file

- audio.motif_asset_id — environment constant, points to the locked motif audio file

- audio.brand_assets_version — version tag, incremented only by deliberate engine update

**Output — what the engine produces**

- Synchronised audio playback at the locked locations. No content-author intervention required.

- A logged event for each playback (for Lock 2 timing analysis and quality monitoring).

**Trigger — when this engine behaviour fires**

- Bell: on every Segment E consequence-horizon transition (Same Day → Next Week, Next Week → Month End). Eight per module, deterministic.

- Motif: on Screen A-0 load; on G-4 Beat 2 entry; on Growth Log first render per session.

**What this engine does NOT do (locked constants)**

- The engine does not allow per-module replacement of the bell or motif

- The engine does not vary volume, fade duration, or pacing per module

- The engine does not add additional audio brand assets through content updates — that requires an engine version increment and a written amendment to this standard

- The engine does not play either asset outside the locked locations — no decorative reuse

**Acceptance criteria — concrete tests**

- In D1, each SC1–SC4 consequence reveal plays the bell at exactly the Same Day → Next Week transition and again at the Next Week → Month End transition. Eight bell strikes total, none missed, none duplicated.

- In D1, the Screen A-0 plays the motif under the wordmark fade-in. Volume and timing match the locked spec. No additional audio plays on A-0.

- In D1, the G-4 Beat 2 silence beat plays the motif during the 2-second hairline fade. The motif resolves before the prompt appears in Beat 3.

- When the participant opens the D1 Growth Log review page for the first time in a session, the motif plays on render. Returning to the same page later in the same session: no replay.

**[MOAT-CRITICAL] — Why this is non-negotiable**

Sonic identity is uncommon in edtech. Apple has its product-launch motif; Bain has its typography. Among the competitors we have surveyed, audio appears to be treated as a content concern, not a brand asset locked at the engine layer. The bell and the motif are sonic signatures that make T3A audibly recognisable within seconds of any module starting. Participants who complete D1 and D2 will recognise the bell on their first scenario in D7. That recognition is what turns a product into a brand. Replacing or varying the audio brand assets per module collapses the signature.

### §1.4.D — Pattern Ledger (Engine Specification) [MOAT-CRITICAL]
Every module renders a cumulative tracking element — the Pattern Ledger — that updates after every scenario decision in Segment E. The Ledger is a persistent visual element. It carries state across scenarios within a single module session and resets between attempts. By the time the participant completes Segment E, the Ledger holds one row per scenario — a complete picture of the choices the participant made and the consequences those choices produced. It surfaces again in Segment G-2 as part of the Growth Log review.

> **⚠️ LOCKED RULE — Pattern Ledger is universal across all modules**
>
> The Pattern Ledger is an engine-level component. The same component renders in D1, D2, D3, and every subsequent module. Module-specific naming is permitted (D1: Integrity Pattern Mirror; D2: Ownership Pattern Mirror; D3: Reliability Ledger; D4 and beyond: dimension-appropriate name). The component, column structure, render logic, and engine behaviour are identical. Every module has a Pattern Ledger; not every module has cross-scenario threading. The Ledger is universal; threading — the use of Ledger state to adapt later-scenario setup narrations — is optional and dimension-specific (see Cross-scenario threading below).

**Column structure (canonical, 4 columns)**

Column 1 — Scenario: short identifier (SC1 through SC4 plus the scenario title).

Column 2 — Commitment: what the participant was responsible for in that scenario, stated in plain language.

Column 3 — Outcome: what happened as a result of the participant’s decision. Descriptive, not evaluative.

Column 4 — Others’ Adjustment: how colleagues, managers, or clients changed their behaviour in response to the participant’s pattern. This is the column that turns the Ledger from a record into a mirror.

**Protected language — Development vs Evidence framing**

Because the Ledger is a cumulative tracking surface, it must be protected from being perceived as evaluation. Every module’s Safety Floor (Screen A-3) carries the Development vs Evidence framing:

*“This is practice and development. Your Growth Log captures what you practised — it is your private development record. Your Skill Passport — if you want documented evidence — is earned through the separate observation pathway. Development is what you do here. Evidence is what the observation pathway produces.”*

**Engine behaviour**

The Ledger is a persistent state object within the module session. It renders as a visual panel after each scenario decision (after the consequence graph, before the next scenario begins). It is mobile-first: scrollable horizontally on narrow screens. Header row stays fixed. On first render after SC1, only the SC1 row is filled; the remaining rows render as empty placeholders — creating anticipation. Each subsequent row animates in over roughly 1.5 seconds at scenario completion. The visual cue is the pattern forming.

The final Ledger state is written into the Growth Log and read by the next module if cross-scenario continuity is part of its design. Lock 2 fingerprint signals related to the Ledger trajectory (e.g., pattern stability across scenarios) are captured developer-only per §1.8.

**Cross-scenario threading (optional, dimension-specific)**

A module may, at its discretion, use the Ledger state to adapt later-scenario setup narrations. This is permitted but not required. When used, the engine implements a state check (count rows where the outcome had “no failure mode activated”) and selects one of three context variants (reliable, mixed, unreliable) for the later scenario’s setup. This is contextual flavour text, not branching. Documented in the module’s production reference.

**Why this is moat-critical**

Most products show the participant one workplace choice in isolation. T3A shows the pattern. The Pattern Ledger is the visible architecture that turns isolated decisions into a behavioural trajectory the participant can see. The “Others’ Adjustment” column is the structural insight competitors miss: behaviour is not judged by whether anyone confronts you — it is judged by how the people around you quietly adjust. Removing or replacing the Ledger with a generic feedback panel collapses the most psychologically realistic moment in the module experience.

### §1.4.E — Participant-Facing Signal Language
> **🔒 LOCKED RULE — No OI/FM codes in participant-facing copy**
>
> Observable Indicator (OI) and Failure Mode (FM) codes are developer-only per §1.8. They appear in no participant-facing UI, no Behaviour Signal Panel, no Reliability Ledger entry, no Growth Log surface. Any per-scenario signal panel surfaced to the participant uses the “What this may signal:” convention with plain-language sentences describing what others may perceive. Producer-side documentation may reference OI/FM codes alongside the participant-facing language, but participant copy never exposes the codes.

**Pattern**

Wrong (participant-facing): “Path A: OI-1 present, OI-2 absent, FM-2 activated.”

Right (participant-facing): “What this may signal: You met the deadline, but the quality gap was hidden. Others may learn to add their own checkpoints around your work.”

The participant-facing version names what others may see and the consequence pattern, never the developer-side classification. This rule applies to every module’s Behaviour Signal Panel, every Reliability Ledger row, and every reflection prompt that surfaces feedback to the participant.

**SCHEMA RECONCILIATION NOTE — Legacy field names in D1**

1. The 19 canonical core fields above remain locked as the target schema for all modules.

3. New modules (D2 onward) must use the 19 canonical core fields from inception. D1's legacy field names are NOT a precedent.

Rationale: this reconciliation prevents drift in D2–D14 (the larger risk) while protecting D1's production readiness (the smaller cost). Silent acceptance of D1's legacy field names as canonical would have encoded the drift into all future modules.

D3 uses this provision for its retrospective decision pause.

- **Story arc:** Single protagonist or relational pair (declared)

- **Resolution at close:** Clean resolution, ambiguous resolution, or open-ended (each appropriate for different dimensions)

- **Required:** At least one artifact-write moment during the audio case (counts toward module's 6-minimum total)

### §2.5 — Variant Generation (Sector Strategy)
> **🔒 LOCKED RULE — MVP scope is single-sector**
>
> Every module ships at MVP with one sector variant only. Additional sector variants (typically 2–3 more) are post-MVP additions, produced after the module has revenue traction. Forcing multi-variant production at MVP triples the consequence-chain writing work and delays revenue.

**Sector variant fields**

- **Change per sector:** industry, role_level, stakeholder_name, constraint_type, artifact_type, pressure_source, vocabulary

- **Constant across sectors:** decision_structure, consequence_logic, OI/FM mapping, signature framework application, central question

**Default MVP sector**

Technology / Software is the default MVP sector across all modules unless specifically justified otherwise. Reasons: largest English-speaking workforce, highest concentration of cross-border professionals, most familiar artifact types (Jira, Slack, Git), and a user base already comfortable with self-serve digital products.

> **🔒 LOCKED RULE — MVP sector limitation must be disclosed honestly in launch copy**
>
> If a module ships at MVP with Technology / Software scenarios only, landing-page and marketing copy must not imply full sector coverage. Buyer-facing claims like "for professionals worldwide" require either (a) sector packs in production for at least 2 additional sectors, or (b) expectation-setting language acknowledging the MVP focus (e.g., "launched with Technology scenarios; healthcare, finance, and public-sector packs coming"). Strategic partner review verifies this alignment before launch. Hidden sector limitations create buyer disappointment that compounds across early adopters and damages the brand more than the limitation itself.

**Axis 2 — Audience-Context Variants [MOAT-CRITICAL]**

Variant calibration has two independent axes. The Industry Sector axis above is Axis 1. The Audience-Context axis (Axis 2) is orthogonal: it captures the participant's career-transition state. The engine composes both axes at module load (see §1.4.B for the engine specification).

The two axes solve different content problems. Axis 1 answers: what does the workplace look like? Axis 2 answers: what is the participant's relationship to that workplace? A healthcare scenario for a Cross-Border Professional inherits the healthcare workplace structure from Axis 1 and adds the cross-border transition framing from Axis 2 (unfamiliar protocols, local unspoken rules, language-register differences, when to ask vs. when to figure it out alone).

**Locked audience-context variants**

- **New Hire** *(default; must be supported by every module)* — Someone in their first 90 days at a new role with a new employer. The primary Probation Blueprint audience.

- **Experienced Worker** — Someone with established workplace experience returning for behavioural calibration. The primary Execution Readiness™ audience (BehaviourLab). Optional per module.

- **Cross-Border Professional** *(locked term — do not substitute **"**newcomer,**"** **"**trans-border,**"** or **"**expatriate**"**)* — A professional who has crossed (or is crossing) a national border to take up a role in a new country. Carries existing professional credentials and is navigating a new workplace culture in parallel with a new job. The primary LMIA/AAIP audience and the WorkRehearsal.com global audience. The institutional category term used by OECD, WHO, ILO, EU. Optional per module at MVP; expected coverage across BridgeFast by end of v1 production.

**What changes per audience-context variant**

- **Changes:** scenario framing additions (unspoken-rules cues, when-to-ask vs. when-to-figure-it-out moments, language-register decisions), participant vocabulary ("your team" vs. "the team you joined two weeks ago"), reflection prompts (transition-aware vs. context-neutral), Recognition Brief examples (cross-border-relevant cases included where helpful).

- **Constant:** decision structure, consequence logic, OI/FM mapping, signature framework, central question. The audience-context axis layers on, it does not rebuild the module.

> **🔒 LOCKED RULE — Every module must support at least one audience-context variant**
>
> At MVP, every module must declare at least one audience-context variant (default: New Hire). Modules may declare additional audience-context variants (Experienced Worker, Cross-Border Professional) when content is ready. The engine's default-tuple fallback ensures every participant receives a complete experience even when their specific tuple has no exact match.

### §2.6 — Lock 2 Fingerprint Per Dimension
Lock 2 is the behavioural fingerprint — proprietary intelligence that compounds with every participant. Each module captures dimension-specific signals in addition to the universal capture set.

**Universal Lock 2 capture (every module, every decision)**

- decision_value (path chosen)

- justification_text (Channel 2 free-form response)

- artifact_write_text (what the participant actually typed)

- deliberation_time_seconds

- composition_time_seconds

- revision_count

- language_features (tone, hedge density, deflection markers — computed post-hoc)

**Dimension-specific Lock 2 signals (declared per module)**

Each module's build worksheet specifies 2–4 dimension-specific signals worth capturing. Examples:

- **D2 (Accountability):** time_to_flag, repair_sequence_completeness, deflection_marker_count, ownership_clarity_score

- **D1 (Integrity):** TBD during alignment exercise — candidates include disclosure_latency, justification_complexity, framing_direction

- **D3–D9:** Declared in build worksheet

> **🔒 LOCKED RULE — Lock 2 signals are never displayed to participants**
>
> All Lock 2 fields appear in no UI, no completion record, and no Growth Log surface. They feed the proprietary intelligence layer that compounds across users. A single leak undermines the long-term IP moat.

### §2.7 — Tiered Innovation Taxonomy
Innovations introduced through module production fall into one of two tiers. The distinction governs whether the innovation propagates back to earlier modules and forward into all subsequent ones, or remains a per-module signature.

**Universal innovations (Standard-wide)**

Innovations that deepen the BridgeFast™ product feel across every module. These are added to this Standard and apply to every module, retroactively if needed. Current universal innovations: Cinematic A-0 entry (§1.9); Cross-module memory contract (§1.4.A); Two-axis variant calibration (§1.4.B); Signature audio brand (§1.4.C); Pattern Ledger (§1.4.D); Participant-facing signal language (§1.4.E); Development vs Evidence framing in Safety Floor; Footer microcopy locked (§1.7).

**Dimension-specific signatures (module-only)**

Innovations that serve a particular dimension’s thesis and would not improve other dimensions if propagated. They live inside the module’s production reference, not in this Standard. Examples: D3’s cross-scenario consequence threading (the Ledger affects later-scenario setup narration); D3’s Pre-Perception Replay (manager perception surfaced before decision); D3’s retrospective decision pause in the Audio Case. Future modules may introduce their own dimension-specific signatures provided they conform to engine and content separation rules per §1.4.

**Promotion path**

A dimension-specific signature may be promoted to universal status if subsequent module production proves it adds value across at least two additional dimensions. Promotion requires updating this Standard and back-porting to all earlier modules where applicable. Promotion is governed by the Moat-Critical Override (§3.0) when the promotion concerns a moat-critical experience element.

## LAYER 3: Quality Gates
What must be true before a module ships. Each gate is sequential — a module cannot pass gate N+1 without passing gate N.

### §3.0 — Governance Principle: Moat-Critical Override
> **🔒 LOCKED RULE — When the Standard and the moat conflict, the moat wins and the Standard amends**
>
> When strict compliance with this Standard would weaken a moat-critical experience element, the module must NOT be weakened. The conflict shall be documented, reviewed, and resolved through a controlled amendment to this Standard. This rule prevents the Standard from becoming a cage that damages the product, while preserving the Standard's authority by requiring every exception to be surfaced, justified, and locked through amendment rather than silent deviation.

**Procedure when a conflict is identified**

1. The producer documents the conflict in writing: which Standard rule conflicts with which moat-critical element, and what specifically would be lost if the module were brought into strict compliance.

2. The Founder reviews. If the moat-critical element is upheld, an amendment to this Standard is drafted to accommodate the module pattern across future modules.

3. The module is held at production-review stage until the Standard amendment is locked. The module ships under the amended Standard, not under silent variance.

4. The amendment cites the moat-critical element invoked (per the [MOAT-CRITICAL] tag system in §1.4) and explains why strict compliance would have degraded the participant experience.

What this rule is NOT: a license for casual deviation. Schedule pressure, scope pressure, engineering convenience, and partner preference are NOT moat-critical concerns and do not trigger this rule. Only documented degradation of a [MOAT-CRITICAL] feature in the participant experience triggers it. Silent deviation under cover of this rule is a Standard violation in itself.

Worked example: §1.3 permits Segment A to use a 5-screen pattern (A-0 through A-4) where the cold-open decision consequence is separately rendered before the safety floor. This protects the sequence pressure → decision → consequence felt → safety floor → central question — moat-critical because the safety floor must land as relief, not as setup. A module that compressed A-2 into A-1 would weaken the experience to fit a stricter screen count; the Standard accommodates the stronger pattern instead.

### §3.1 — The 4-Round Destruction-Rebuild Cycle
**Every module passes through four rounds, in order**

The 4-round cycle was established during D1 production and validated during D2 production. It is now the standard for all modules. Each round has a specific destruction focus, a rebuild scope, and a verification checklist. Skipping a round produces structurally incomplete modules.

| **Round** | **Focus** | **Destruction concerns** |
| --- | --- | --- |
| **Round 1** | **Emotional rebuild** | Cold open, awe close, signature framework restructure (recognition before naming), artifact-write threading. Does the module feel like a premium rehearsal? |
| **Round 2** | **Doctrine** **& developer rules** | Banned-term audit, vocabulary lock, MVP variant narrowing, marketing-page extraction, module title lock, developer-only visibility enforcement. |
| **Round 3** | **Break-point visibility** | Pause-anytime vs structured break point distinction. 3-tier Smart Resume protocol. 4 structured break points placed at natural rest moments. |
| **Built** | **Premium-experience spec additions** | Screen A-0 entry beat detail. Sound & voice design. Artifact visual design. Growth Log review. Avatar casting notes. Mobile-first detail notes. |

### §3.2 — Banned-Term Audit
Automated pass. Every module's participant-facing copy is scanned against the banned-term list in §1.6 before strategic partner review. A single occurrence fails the audit and requires correction.

Banned-term audit is also re-run after every revision pass throughout the cycle. The list does not shrink; it occasionally grows when new patterns emerge.

### §3.3 — Schema Validation
Every module passes a schema validation check before going to engineering. The check confirms:

- All active schema fields present (19 core + 5 extensions = 24 total)

- All active schema fields have valid values for the field type (19 core + 5 extensions)

- Cross-references resolve (e.g., dimension.framework.label appears in recognition_briefs.frameworks[])

- Scenario consequence horizons match a valid set from §2.3

- Artifact-write count meets the minimum (6 across the module)

- Observable indicators and failure modes are dimension-specific and not borrowed from another module's set

### §3.4 — Strategic Partner Review Threshold
After all four destruction-rebuild rounds, the module goes to strategic partner review. The review applies a 0–100 score across:

- Brand clarity

- Premium feel

- Buyer trust

- Conversion readiness (where applicable)

- Legal / safety wording

- Emotional pull

> **🔒 LOCKED RULE — Minimum score to ship: 85/100**
>
> A module scoring below 85 returns for further revision. A module scoring 85–94 is launchable but should be marked for post-launch refinement. A module scoring 95+ is the standard. The score is honest — inflating it to ship faster is forbidden, because it corrupts the calibration of future modules.

### §3.5 — Standard & Engine Alignment Check
Every module after D1 must pass alignment against this Dimension Production Standard and the D1 engine baseline. The check is structural, not stylistic — it ensures the new module matches the architecture, doctrine compliance, and documentation completeness specified in this standard, and that it loads cleanly against the existing engine that D1 first validated.

**Alignment check items**

- Same 7-segment structure

- Same canonical schema (19 core + 5 extensions)

- Same documentation structure (cover, doctrine page, TOC, segments, schema map, 8 appendices, retention library, closing for Hans)

- Same banned-term compliance

- Same locked vocabulary usage

- Same Lock 2 universal capture set

- Same break-point architecture

- Same Smart Resume protocol

**Alignment is not stylistic mirroring**

Alignment means structurally matched to this standard. It does not mean a new module should sound like D1, feel like D1, or carry the same emotional register as D1. Dimensional calibration (Layer 2) is preserved. The structural skeleton is what is aligned. D1 remains a useful reference for engine compatibility, not a constitutional authority.

### §3.6 — Engine Compatibility Test
Hans's engineering pass. The module's content is loaded into the BridgeFast engine with dimension_id swapped to the new module. The test passes if:

- All 24 active schema fields parse without error (19 core + 5 extensions)

- All 4 scenario chains render correctly

- All 36 consequence narrations display in the correct horizon

- All artifact-writes save and recall correctly (including cold-open threading)

- All break-point invitations appear at the specified moments

- Smart Resume returns the correct screen on resume from each tier

- Growth Log entries write correctly

- Lock 2 capture writes without exposing to UI

> **🔒 LOCKED RULE — Engine compatibility is the final gate**
>
> A module that fails engine compatibility goes back to content production, not to engineering. If the engine cannot run the content, either the content violates the standard, or the standard needs to be updated and the engine adjusted. The default assumption is the content violates the standard.

### §3.7 — Market Defensibility Gate [MOAT-CRITICAL]
The Market Defensibility Gate is the final pre-ship review. It exists because the [MOAT-CRITICAL] tag system protects existing features, but does not force a new module to demonstrate that its differentiation is not market-common. §3.7 closes that gap.

Before a module ships, it must demonstrate that it does not rely on market-common features as its primary differentiation. Market-common features are widely available across competing platforms and cannot, on their own, distinguish T3A.

**Market-common features (these alone do NOT pass the gate)**

- Simulation, role-play, immersive scenarios

- AI feedback, AI-powered coaching prompts, AI role-play partners

- First-90-days pathways, 30-60-90 frameworks, onboarding journeys

- Personalised practice, adaptive pathways, soft-skill training

- LMS-style progress tracking, completion certificates, dashboards

**Moat elements (a passing module shows at least four, active in the participant experience)**

- Cinematic pressure entry (Screen A-0, un-skippable, restraint by design)

- Artifact-write with reference calibration (three reference versions)

- Three-horizon consequence threading (Same Day / Next Week / Month End)

- Cross-module memory consumption — where applicable to the module's sequence position (D1 has no prior modules to consume from; producing the emission contract for D2 to consume still counts here)

- Two-axis variant calibration — where applicable to the module's scope (modules supporting only New Hire still demonstrate Axis 2 architecture; modules supporting additional audience contexts demonstrate it in content)

- Signature framework carry-out (the dimension's framework lands in the participant's words, not as a label)

- Manager Lens or Perception Replay (where the module includes a supervisor or third-party vantage)

- Growth Log continuity (the participant's decisions, reflections, and artifacts persist as a personal record, not as a score)

- Retention check as re-rehearsal — canonical at MVP per §1.4

- Signature audio brand (bell at consequence-horizon transitions; motif at Screen A-0, G-4 silence, Growth Log header)

**Pass threshold**

A T3A module passes only if the reviewer can identify at least four active moat elements in the participant experience, drawn from the list above. "Active" means visible or audible to the participant during the module — not declared in documentation but absent from the build. The "where applicable" modifier protects modules whose sequence position or scope makes a given moat element structurally impossible (e.g., D1 has no prior module to consume from). A reviewer must not fail a module for an inapplicable element.

**Failure routing**

A module that feels like a course, an onboarding pathway, a role-play tool, or an LMS activity has failed this gate. It returns to destruction-rebuild review (§3.2–§3.4) regardless of how well it passes the prior gates. Engine compatibility (§3.6) without market defensibility (§3.7) is a competitor's product built on T3A's engine. Before re-entering destruction-rebuild, the producer re-reads the front-matter section "Market Position and Moat-Critical Features," with attention to the side-by-side comparison table and the four-line "What the participant feels" check. A module that fails this gate has failed against that comparison; the destruction-rebuild pass should target the specific moat element(s) absent or degraded in the participant experience, not produce a uniformly stronger module.

**[MOAT-CRITICAL] — §3.7 cannot be relaxed**

§3.7 is itself a moat-critical rule. It exists because the most likely failure mode in T3A's first eighteen months is silent feature parity — a module shipping that passes all prior gates while being indistinguishable from a competitor's product on the participant's actual screen. The Market Defensibility Gate exists to catch that failure before the participant does. It cannot be bypassed for schedule, scope, or convenience. Any proposed exception requires founder review and a written amendment to this standard.
