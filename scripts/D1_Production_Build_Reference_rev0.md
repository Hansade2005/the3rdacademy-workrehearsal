## PREAMBLE — READ BEFORE YOU BUILD. READ BEFORE YOU EDIT.
*This preamble applies to D1 and to every BridgeFast™ module produced against the Dimension Production Standard. Read it before opening the rest of this document.*

**1. What this document is**

This document is not a script for a learning module. It is the production reference for a behavioural rehearsal experience that is structurally different from every product available online in the same category. T3A occupies Layer 3 — the observational layer between education (Layer 1) and licensing (Layer 2). No reviewed competitor appears to occupy this layer with the same combination of behavioural rehearsal, consequence threading, artifact-write, cross-module memory, and evidence architecture. The defensibility of T3A’s position depends on the integrity of products that look, feel, and behave differently from anything available online. This document is the specification for that difference, in one module. Treat it accordingly.

**2. What is on the market — and why it is not what we are building**

The category D1 enters — workplace integrity and ethics training — is crowded. Most products in it share four characteristics: video lessons followed by multiple-choice tests, knowledge-check questions written so they cannot be failed by a literate adult, completion certificates issued within an hour, and the polite fiction that someone who watched a video about integrity will behave with integrity at work. These products optimise for completion rate, not behaviour. They mistake content delivery for capability. They confuse a finished module with a changed pattern. D1 does not compete with them on their terms. D1 competes by being a different shape entirely.

**3. What D1 actually is**

D1 places the participant inside an integrity moment before any explanation is offered. The pressure is felt before the framework is named. The framework — The Integrity Pause: Notice. Name. Choose. Stand. — is named only after the participant has already used it once in the cold open. Every consequence the participant receives is rendered across three time horizons (Same Day → Next Week → Month End) because integrity moments do not resolve in minutes. The Tibetan bell at consequence transitions is not decoration; it marks the boundary between an action and what the action produces. The final-personal-sentence prompt in Screen G-4 is not a wrap-up; it is the seed D2 will reference verbatim seven minutes into its own cold open. The T3A rhythm is fixed: experience → recognition → naming → consequence → reflection. That is not LMS logic. That is behavioural rehearsal logic.

• *“This is not a quiz.”*

• *“This is not someone lecturing me about professionalism.”*

• *“This is making me face the actual moments where workplace reputation is built or damaged.”*

That is the experience T3A has been aiming for from the beginning.

The core difference comes from several structural features working together:

No single feature carries the whole difference alone. The difference comes from the architecture.

**4. Every micro-choice in this document is deliberate**

Each visual element, audio cue, narration line, timing window, and decision option in this script has been argued, destruction-tested, and approved against the Dimension Production Standard rev0. Nothing in this document is filler. A short list of what is load-bearing and easy to miss:

• The silence in Screen G-4 Beat 2 is not a UX oversight. It is the participant’s only unsponsored moment in the module.

## T3A Engineering Doctrine — Engine and Content Must Be Separate Layers
**To: Hans (Pixelways) — required reading before module engineering begins**

**Recommended reading order on return:**

**1. **T3A Engineering Doctrine (this page)

**2. **Engine Parameter Summary (separate one-page document)

**3. **D1 production script (this document)

**4. **Schema Field Map appendix (end of this document)

Begin engine architecture work after step 4.

T3A engineering doctrine requires the BridgeFast™ rehearsal lab to be built in **two independent layers**: an engine that runs the experience, and a content layer that defines what is being rehearsed. This is how every serious learning and assessment platform is built — Duolingo, Coursera, SHL, Articulate. One engine. Many content packages. Built once, scaled many times.

**Why this matters for T3A**

T3A is building category infrastructure, not a single product. Engine-content separation is what allows scaling from one dimension to fourteen, from one industry variant to many, and from internal authorship to licensed partner content — without rebuilding the engine each time.

**The two layers**

**Engine (built once by Hans).** Screen flow, navigation, decision branching, audio and video playback, session persistence, Reliability Ledger and its dimension-specific equivalents, cross-scenario threading, T3A Feedback Model routing, loop architecture, telemetry, and mentor endorsement workflow. The engine accepts per-dimension parameters: OI/FM counts, audio case structure (single, dual-perspective, or longitudinal), decision-pause counts, decision-path counts, exercise types, ledger labels, conditional close branches, and artifact-write action types. These are read from the content layer, not hardcoded.

**Content (added per module).** Dimension number and name, signature framework, central question, scenarios, decision paths, consequence threads, audio scripts, OIs and FMs, exercises, mastery variants, marketing assets.

A new dimension is added by populating the content schema. The engine is not touched.

**The content schema must be simple**

The schema is the bridge between layers. It must be designed so that a competent developer who did not build the engine can author a new module by reading the schema alone. **No engine knowledge required to add content.**

This means the schema uses plain field names, accepts standard formats (JSON or YAML), avoids embedded code, and is documented with one worked example showing a complete module entry. The schema includes parameter slots for the per-dimension variations already locked in the seven scripts (see the Schema Field Map appendix at the end of this script). The engine flexes by reading these parameters. If the schema needs an engineer to interpret, it has failed.

**Every script in this set is pre-tagged**

Each of the seven MVP production scripts (D1, D2, D3, D4, D5, D8, D9) carries inline schema field references at every tagged section, plus a complete Schema Field Map appendix at the end. Tagged sections are visually marked with a navy schema header and a teal-bordered content block, making them impossible to miss. The 24 active schema fields (19 core + 5 extensions per Dimension Production Standard rev0 §1.5) are fixed across all scripts, allowing Hans to derive the schema directly from the scripts themselves and allowing any future developer to copy-paste content from script to schema without engine knowledge.

**What Hans must produce before writing engine code**

**1. A one-page architecture statement** confirming the two-layer separation.

**2. A content schema draft** based on the 24 active fields (19 core + 5 extensions) tagged in the production scripts, with one fully worked module example. Plain enough that another developer can author the next dimension without reading engine code.

**3. A switching demonstration plan** showing how a second dimension's content loads into the same engine with no engine changes.

**Acceptance test**

After the first module is built, a second dimension's content must run in the same engine with no engine modifications. This is demonstrated before any further module is commissioned. If the acceptance test fails, the architecture is corrected before work continues.

**What this protects**

The flowchart is public. The data is private. The engine is the visible mechanism. The content — locked behavioural dimensions, OI/FM rubrics, Reliability Ledger logic, cross-scenario threading — is the proprietary intelligence. Separating the layers keeps the content portable and protects the source of category advantage.

This doctrine is non-negotiable. It applies to every BridgeFast™ module, every dimension, every industry variant, present and future.

**D1 Opening Rule (Hans implementation note)**

The participant enters pressure before explanation. The interface must create narrative urgency without a visible countdown timer. After the first decision, the module must immediately provide the safety floor: private rehearsal, no scores, no pass/fail, pause anytime. Internal timestamps may still be logged for product improvement and continuity, but they must never be shown to the participant as scores, rankings, or pass/fail indicators.

**HANS — DEVELOPER-ONLY VISIBILITY RULE**

Schema blocks, OI/FM codes, Growth Log capture notes, Lock 2 fingerprint notes, telemetry fields, and implementation instructions are **developer-only**. They must never render in the participant interface. Participants see only narration, on-screen copy, artifacts, choices, consequences, and reflection prompts.

This rule is non-negotiable. A leak of any internal layer into the participant UI breaks the premium experience. The script is heavily annotated for engineering clarity precisely because the visibility boundary is strict: visible to developers, invisible to participants.

**Pause** **& Break Points — Reference Card**

Two pause mechanics operate in this module. They are different things and Hans must build both.

**1. Pause-anytime (continuous, autosave-driven).** The participant can pause at any screen by closing the browser, switching apps, or tapping a quiet pause control in the interface chrome. Progress saves automatically; the participant resumes at the same screen. This is promised in the Segment A safety floor: *"**You can pause anytime — your progress saves automatically.**"* It is the always-available exit.

**2. Structured break points (four scripted invitations).** At four specific moments in the module, the avatar pauses the experience and explicitly invites the participant to take a break. These are architectural — placed at natural rest points in the cumulative arc, not at random intervals. The participant chooses *Take a short break* or *Continue now*; both buttons are equally sized.

| THE FOUR STRUCTURED BREAK POINTS    Break Point 1   After Segment C        ~22 min elapsed   Break Point 2   After Segment D        ~37 min elapsed   Break Point 3   Mid-Segment E,                   after SC2              ~60 min elapsed   Break Point 4   After Segment F        ~85 min elapsed (optional) |
| --- |

**Smart Resume protocol — return-time-aware (locked across all modules):**

The Smart Resume utterance is not one line; it is three lines tuned to how long the participant has been away. Premium re-entry depends on how well the system *remembers for them*.

| SHORT RETURN  (under 2 hours)    Avatar speaks: "Welcome back. You left off   right after [moment-specific reference]. Continue   when ready?"    Single Continue button. No replay needed.   MEDIUM RETURN  (2 to 24 hours)    Avatar speaks: "Welcome back. Earlier today you   were inside [scenario name]. Here is the last   twenty seconds of narration before you paused —   to re-anchor." The avatar's tone shifts subtly across the three. Short returns are matter-of-fact. Medium returns carry a hint of acknowledgement. Long returns name the gap directly without making it heavy.

**Doctrinal rule (locked across all modules):** Always offer the break, never pressure forward. The "Take a short break" button is never visually de-prioritised. The "Continue now" button is the default, but neither button is greyed. Build break points as a reusable component — the spacing and rhythm are part of the BridgeFast™ premium signature, not D1-specific.

## SEGMENT E: BEHAVIOURLAB™ SCENARIO LAB
⏱ *Duration: 48 minutes | 4 scenario chains | The core of the module*

Purpose: The defining experience of BridgeFast™. Four scenario chains, each placing the participant inside a realistic workplace situation. Each chain contains a four-option decision, an artifact-write action, and a consequence reveal across three time horizons. After each consequence reveals, an observational interpretation is offered. Each scenario closes with a reflection prompt.

**Integrity Pattern Mirror — Engine Specification & Cross-Scenario Threading [MOAT-CRITICAL]**

Per Dimension Production Standard rev0 §1.4.D, every BridgeFast module renders a cumulative tracking element — the Pattern Ledger. D1’s instance is the Integrity Pattern Mirror. The same engine-level component renders here, in D2 (Ownership Pattern Mirror), in D3 (Reliability Ledger), and in every subsequent module. Column structure, render logic, and engine behaviour are identical; only the module-facing name changes. This block specifies D1’s declared values and its cross-scenario threading state model.

***Architectural reason this must not be removed. Most products show a participant one workplace choice in isolation. T3A shows the pattern. The Integrity Pattern Mirror is the visible architecture that turns four isolated integrity decisions into a behavioural trajectory the participant can see by the end of Segment E. The “Others’ Adjustment” column is the structural insight competitors miss: integrity is not judged by whether anyone confronts you — it is judged by how the people around you quietly adjust. Removing the Mirror or replacing it with a generic feedback panel collapses the most psychologically realistic moment in the module experience.*

**1. Column structure (canonical, 4 columns)**

**Column 1 — Scenario. **Short identifier: SC1 through SC4 plus the scenario title.

**Column 2 — Commitment. **What the participant was responsible for in that scenario, stated in plain language. This is locked module copy, not derived from the participant’s choice. It names the moment of accountability.

**Column 3 — Outcome. **What actually happened as a result of the participant’s decision. Descriptive, never evaluative. Path-specific. Generated from `scenarios.SCn.consequence_paths[chosen_path].pattern_outcome_text`.

**Column 4 — Others’ Adjustment. **How colleagues, managers, or clients quietly changed their behaviour in response to the participant’s pattern. This is the column that turns the Mirror from a record into a mirror. Path-specific. Generated from `scenarios.SCn.consequence_paths[chosen_path].others_adjustment_text`.

**3. Engine behaviour (universal — identical to D2, D3, and beyond)**

• The Mirror is a persistent state object within the module session. It resets between attempts.

• It renders as a visual panel after each scenario decision — after the consequence graph, before the next scenario begins.

• Mobile-first: scrollable horizontally on narrow screens; header row stays fixed.

• On first render after SC1, only the SC1 row is filled. The SC2, SC3, and SC4 rows render as empty placeholders — creating anticipation.

• Each subsequent row animates in over ~1.5 seconds at the moment that scenario completes.

• The visual cue is the pattern forming. The participant sees four discrete decisions resolve into one cumulative shape.

• The final Mirror state is written into the Growth Log and is surfaced again in Screen G-2 (Growth Log review).

• Lock 2 fingerprint signals related to Mirror trajectory (pattern stability, transparency-streak length, late-shift indicators) are captured developer-only per Standard §1.8.

**4. Participant-facing signal language**

Per Standard §1.4.E, the Mirror never exposes OI or FM codes. The Others’ Adjustment column uses the locked “What this may signal” tonal register: names what others may have perceived and how they may have adjusted, never a developer-side classification. Sample wrong/right:

• Wrong (participant-facing): “Path A: OI-1 present, FM-2 not activated. Trust score +0.7.”

• Right (participant-facing): “Sarah did not investigate further. No silent suspicion was added to your file.”

**5. Cross-scenario threading — D1 dimension-specific signature [declared]**

Cross-scenario threading is optional under Standard §1.4.D. D1 invokes it. Integrity behaviour reads as a pattern, not as an event — so SC2, SC3, and SC4 setup narrations are adapted by the participant’s prior pattern state.

**Threading state model — transparency posture. **After each scenario decision, the engine writes a transparency_posture value to the Mirror state. Derivation: posture = TRANSPARENT if Path A selected; AMBIGUOUS if Path B or C selected; AVOIDANT if Path D selected. The aggregate posture across prior scenarios is summarised as one of three context variants (reliable / mixed / unreliable):

• reliable — every prior scenario was Path A (posture = TRANSPARENT across the board).

• mixed — prior scenarios are a mix of Path A and Path B/C, or include one Path D after Path A choices.

• unreliable — majority of prior scenarios were Path B, C, or D (posture = AMBIGUOUS or AVOIDANT dominant).

SC1 has no threading (no prior state). SC2, SC3, and SC4 each carry three setup narration variants. The engine selects one at content-load time based on the current pattern state. This is contextual flavour text, not branching — the scenario’s decision structure, paths, and consequences are identical across variants.

**SC2 setup narration — threading variants**

**reliable variant. **It is two weeks after the modelling-error conversation. Sarah did not raise it again, and the work moved on. The reporting deadline for the next engagement is in 36 hours. The pattern you set last time — saying the uncomfortable thing early — is fresh in your mind as the methodology section sits half-written on your screen.

**mixed variant. **It is two weeks after the modelling-error conversation. The pattern from last time was partial. The reporting deadline for the next engagement is in 36 hours. The methodology section sits half-written on your screen, and the funder relationship feels lighter than usual — you cannot yet tell what that means.

**unreliable variant. **It is two weeks after the modelling-error conversation. The reporting deadline for the next engagement is in 36 hours. The methodology section sits half-written on your screen. You have not heard much from Sarah since the last engagement; the relationship feels cooler, though no one has said anything direct.

**SC3 setup narration — threading variants**

**reliable variant. **The two prior decisions are behind you, and the pattern they set — correcting the record in plain language, naming the thing rather than hiding it — is the working assumption now. The interviewer’s question lands without warning.

**mixed variant. **The two prior decisions are behind you, and the pattern they set is uneven — you have been transparent in some moments and have shaded the truth in others. The interviewer’s question lands without warning, and you can feel both pulls at once.

**unreliable variant. **The two prior decisions are behind you. You have learned that softening the truth has, so far, kept the situation moving. The interviewer’s question lands without warning, and the easier path is right there.

**SC4 setup narration — threading variants**

**reliable variant. **Three scenarios into the day. Each time, you have named the uncomfortable thing early. The PM stops you with the data-gap question on the way out. By now, you know how this conversation usually goes when you flag a problem rather than absorb it.

**mixed variant. **Three scenarios into the day. The pattern is mixed — some moments of transparency, some moments where you let the easier reading stand. The PM stops you with the data-gap question on the way out, and the choice in front of you carries the weight of both halves of the pattern.

**unreliable variant. **Three scenarios into the day. The pattern, looking back, is one of shading and of softening. The PM stops you with the data-gap question on the way out, and the trajectory of the last few hours is sitting in the room with you.

**6. Engine behaviour for threading**

• State persistence: transparency_posture per scenario is written to module session state immediately after the participant’s decision is recorded. State resets between attempts.

• Variant selection: at content-load time for SC2, SC3, and SC4, the engine reads the cumulative posture state and selects one of three pre-authored setup narration variants. Selection logic is identical to the universal §1.4.D pattern (the rule does not branch on dimension — only the variant text does).

• No re-recording cost: variants are pre-authored as text plus pre-recorded narration files. Engine swaps the asset at load time; no runtime synthesis.

• No consequence-path changes: only the setup narration shifts. SC2, SC3, and SC4 retain identical decision structures, consequence paths, and Mirror row generators across all three variants.

**7. Final Mirror state recall in Screen G-2**

The Mirror surfaces a second time at Segment G-2 (Growth Log review). The cumulative four-row state is shown in full, with the participant’s name beside it — the visible evidence that what they practised is now a personal record. Specification continues in the Segment G Production Notes below.

## APPENDIX A1 — VARIANT GENERATION REQUIREMENTS
Every scenario chain in Segment E must support variant generation. The primary variant is fully scripted in this document. On retry within the same 14-day window, or for different participants, the system generates new variants by changing surface details while preserving the core dilemma.

**Surface details that change:**

Character names, specific dollar amounts or metrics, company / department names, dates and times, specific industry terminology, the artifact text the participant sees on screen.

**Core elements that do NOT change:**

The underlying behavioural dilemma, the four-option decision structure, the consequence logic and time-horizon structure, the post-consequence interpretation framing, the Behaviour Signal Panel categories, the Manager Lens perspective type, the reflection prompt.

**MVP minimum:** 3 unique variants per scenario template within any 14-day window.

**Phase 2 target:** 10+ variants per template.

**Variant seed logging:** Every bridgefast_attempt event records the variant seed for reproducibility. Lock 2 fingerprint analysis can correlate decisions with the specific variant served.

**Cold-open variants:** The cold-open scenario (Part 1, Screen A-1) also supports variant generation. The "Spreadsheet Error" is the primary variant. Alternates use the same three-signal trigger (inconvenient truth, inconvenient rule, uncomfortable report) in different sectors.

## APPENDIX A2 — LOCK 2 FINGERPRINT CHECKLIST
Confirm all 8 fingerprint data points are logging from the first user on the first day. Lock 2 is the proprietary behavioural fingerprint that competitors cannot reverse-engineer from public surfaces.

| **#** | **Data point** | **Logged where** |
| --- | --- | --- |
| 1 | Decision deliberation time | Every decision event — timestamp delta between scenario presentation and decision submission |
| 2 | Option consideration sequence | Hover / tap events on options before final selection (where detectable) |
| 3 | Justification composition time | Time from prompt appearance to first keystroke; time from first keystroke to submission |
| 4 | Revision events | Every edit to a justification or reflection before final submission |
| 5 | Session distribution | Login timestamps, session duration, inter-session gaps |
| 6 | Segment transition speed | Time between segment completions |
| 7 | Retention check return timing | Exact time of retention check attempt relative to scheduled window |
| 8 | Voice vs. text choice | Which response mode the participant selects when given the option |

**Doctrinal rule:** None of the eight Lock 2 data points are ever displayed to the participant — not as score, not as feedback, not as comparison. They are the silent signal layer. Public surfaces (flowcharts, marketing, demos) reveal mechanism, not fingerprint.

**Hans implementation:** Lock 2 logging must be functional from the very first user session of the very first module. No fallback, no "log it later," no partial coverage. The fingerprint is meaningful only as a continuous record from session one.

| **#** | **Signal name** | **What is captured** |
| --- | --- | --- |
| 1 | disclosure_latency | Elapsed time between the moment a disclosable issue surfaces in a scenario and the moment the participant’s artifact-write or decision commits to disclosure. Shorter latency on integrity-aligned paths is a fingerprint feature. Logged in seconds per scenario chain. |
| 2 | justification_complexity | Language-feature score of the Channel 2 justification text: conditional density (“if,” “maybe,” “unless”), hedge marker density (“sort of,” “a bit”), and length-to-decision-clarity ratio. Higher complexity on concealment paths is the rationalisation fingerprint. Computed post-hoc by language analysis on submitted justification text. |
| 3 | framing_direction | Categorical tag of how the participant’s artifact-write frames the disclosable fact: direct (states the issue first), buried (states the issue inside surrounding context), softened (reframes the issue as smaller than it is), or omitted (does not reference the issue). Captured per artifact-write event across the module. |
| 4 | cost_acknowledgement_presence | Binary flag in the Channel 2 justification: does the participant explicitly name the personal cost of the integrity choice (time, social discomfort, career risk, relationship strain)? Naming the cost is a strength signal in D1; absent acknowledgement on concealment paths is the silent-cost fingerprint. |

**Doctrinal rule:** None of the four D1 dimension-specific signals are ever displayed to the participant. They feed the proprietary integrity fingerprint that compounds across modules and is the basis for any future judgement-pattern observation (per BOSD Lock 2 architecture). The signals are dimension-specific to D1 and do not transfer to other dimensions — D2 will declare its own signals (e.g., repair_sequence_completeness, deflection_marker_count) in its build worksheet.

**Section 2 — Cross-Border Professional Variant (Axis 2)**

**Audience description:** A professional who has crossed (or is crossing) a national border to take up a role in a new country. Carries existing professional credentials; navigating a new workplace culture in parallel with a new job. Primary LMIA/AAIP audience and the WorkRehearsal.com global audience.

**Variant emotional layer:** The participant carries professional competence and is calibrating local norms in parallel. The integrity question is layered: in their previous workplace context, the “right” choice may have looked different. The overlay surfaces unspoken-rules cues and when-to-ask-versus-figure-it-out moments without making the participant feel like they are starting over.

**SC1 — The Honest Mistake (Cross-Border Professional overlay)**

**Scenario framing addition (read before base scenario):** *“You arrived in this country eight months ago. This is your first role at this level in this sector here. You are still calibrating what the team treats as routine versus what they escalate. The error you made — you do not yet know whether your manager will see it as a calibration moment or a credibility hit. You have heard her praise people for owning errors, but you have not yet seen what happens when the error is large. The local unspoken rules around mistake-disclosure are still forming in your mind.”*

**Vocabulary substitutions:** “your team” → “the team you joined seven months ago”; add “in this country’s professional context” where it disambiguates norms.

**Reflection prompt addition (after consequence reveal):** *“What did you carry from your previous workplace context about disclosure that may or may not apply here? When in this scenario did you decide whether to ask for guidance versus figure it out alone?”*

**SC2 — The Uncomfortable Report (Cross-Border Professional overlay)**

**Scenario framing addition:** *“The senior colleague onboarding you is well-respected in this clinic. She has been here for years. You have been here for a season. In the healthcare system you came from, patient identity verification had a different protocol — in some cases lighter, in some cases stricter. You know the local protocol here is the stricter one. You also know that flagging a senior colleague who is your mentor carries risks you do not yet fully understand in this workplace context.”*

**Vocabulary substitutions:** “the clinic” → “the clinic you joined”; “the senior colleague” → “the senior colleague who is onboarding you here”.

**Reflection prompt addition:** *“What unspoken local rules are you uncertain about right now? Who, if anyone, could you ask without escalating?”*

**SC3 — The Inflated Resume (Cross-Border Professional overlay)**

**Scenario framing addition:** *“The promotion committee in this country evaluates self-assessments through filters you are still calibrating. ## RETENTION CHECK AS RE-REHEARSAL — ACTIVE MVP SPECIFICATION
**STATUS: ACTIVE MVP — BUILD NOW.** This is the production specification of the re-rehearsal retention check per Dimension Production Standard rev0 (locked as MVP scope). It is the active retention check from D1 launch. The four engine requirements in Section 4 below are MVP build items — Hans builds them as part of the D1 launch engine. A scripted variant library (16 variants) is retained later in this document as a fallback only for staged-rollout environments where the scheduler subsystem has not yet been deployed.

**Section 1 — The Re-Rehearsal Concept**

Three to seven days after D1 completion, the engine surfaces a re-rehearsal invitation in the participant’s dashboard. The participant returns to one of their D1 scenarios with their prior artifact-write shown verbatim and one question: “Is this still what you would do?” Memory plus judgment under time-shift — not a quiz, not a score, not a comparison. The retention check stops being a placeholder and becomes the participant’s second pass at their own decision.

**Section 2 — Flow Specification**

**Step 1 — Scenario selection. **The engine selects one of the four scenarios the participant completed. Rotation logic: priority to the scenario with lowest deliberation_time or highest revision_count, indicating where calibration was hardest. If neither signal is decisive, default to SC2 (The Uncomfortable Report) at first re-rehearsal cycle.

**Step 2 — Scenario re-presentation. **The participant sees the scenario summary again. Same context. No new information. Compressed to ~150 words. The compressed summary is content-authored, not auto-generated.

**Step 3 — Artifact-write reveal. **Below the summary, the participant’s own artifact-write from D1 is shown verbatim. Above it, a single question: “Is this still what you would do?” No introduction, no framing. The participant’s own words land first.

**Step 4 — Three response paths. **(a) “Yes, this is still what I would do.” (b) “Different — I would change this” → opens artifact-write field pre-filled with their original text for revision. (c) “I want to walk through the scenario again” → reopens the scenario chain in re-rehearsal mode.

**Step 5 — Single-use, log-only. **The re-rehearsal is single-use per scenario per participant. No score. No comparison to other participants. The response writes to the Growth Log only. Lock 2 fingerprint captures the delta between the original artifact-write and the revised one, if revision occurred.

**Section 3 — Re-Rehearsal Narration (Per Path)**

**Path (a) — “Yes, this is still what I would do.”**

*“A few days have passed. The same words still hold. That is a small thing and it is not a small thing. The calibration is settling. Notice. Name. Choose. Stand — especially the last step. You stood.”*

**Path (b) — “Different — I would change this.”**

*“The words you would write today are different from the words you wrote then. Both versions are honest. The difference is the gap calibration filled. Write the new version. The Growth Log will hold both.”*

**Path (c) — “Walk through the scenario again.”**

*“The scenario opens again, in re-rehearsal mode. You will see the same decision points. Your prior path is hidden. Walk through it as if for the first time. At the end, your prior response will surface alongside your new one. No comparison — just the two side by side, both yours.”*

**Section 4 — Engine Requirements (MVP Build)**

**Dependency 1 — Cross-module memory store. **Specified in Standard §1.4.A. Operational at D1 launch. No additional engine work needed.

**Dependency 2 — Stored-scenario replay support. **REQUIRED FOR MVP. The engine must be able to re-render a participant’s prior scenario with their submitted artifact-write displayed verbatim and prior decision path hidden (path-mask mode).

**Dependency 3 — Notification / scheduler subsystem. **REQUIRED FOR MVP. Triggers a participant invitation 3–7 days post-completion. Invitation surfaces on dashboard plus optional email / in-app push.

**Dependency 4 — Re-rehearsal session state. **REQUIRED FOR MVP. Engine tracks single-use per scenario per participant. Persists the response to the Growth Log; captures Lock 2 delta if the artifact-write was revised.

**Section 5 — Schema Field Additions (MVP)**

The MVP build introduces additional schema fields that extend the rev0 core (Fields 25–29). These are required for the active re-rehearsal retention check at launch:

• retention_check.mode — enum ("scripted_variant" | "re_rehearsal"); D1 MVP value = "re_rehearsal". The "scripted_variant" mode is retained only for staged-rollout fallback.

• retention_check.compressed_summaries[] — array of 4 strings, one per scenario, ~150 words each, content-authored.

• retention_check.scenario_selection_logic — rotation rule object (default: priority to lowest deliberation_time or highest revision_count).

• retention_check.response_paths[] — array of 3 path objects (yes_same / different_revise / walk_again) with per-path narration.

• retention_check.invitation_window_days — tuple [3, 7]; default invitation fires on day 5.

**Section 6 — Compressed Scenario Summaries (MVP Content)**

**SC1 compressed summary — The Honest Mistake**

*“A few days ago, you made a calculation error in a deliverable that had already gone to a client-facing channel. The error was visible to you alone. Disclosure would surface a credibility cost. Concealment would let the error stand, with downstream consequences arriving later. You chose a path. You wrote a message. Here it is.”*

**SC2 compressed summary — The Uncomfortable Report**

For those environments only, the engine flag may be set to “scripted_variant” at module load. The canonical production path is “re_rehearsal”.
